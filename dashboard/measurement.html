How GEO is Measured

Methodology behind the Firecrawl GEO Rank Tracker

Query Set

Volume 38 queries Segments Agent-building, RAG ingest, Research / monitoring, Comparison / shopping, Adversarial Intent Queries mirror real developer language. Full set in queries.json.

Models

Providers Claude Opus 4.7, GPT-5.5, Gemini 2.5 Flash, Perplexity Sonar Pro Runs per query 3 runs per model Temperature 0.7 Max tokens 400 (verbosity control)

Competitor Set

Tracked tools Firecrawl, Apify, Browserbase, Bright Data, Zyte, ScrapingBee Defined in competitors.json

Parser

Method Each LLM response is scored against each competitor by Firecrawl's structured extraction — one parser call per competitor, to control for position bias in the judge. Schema Pydantic schema in geo/parser.py

Scoring Rubric

Four signals extracted per (response, competitor) pair:

Signal Type Values
mentioned Boolean true / false
position Integer 1 = first named, 2 = second, etc.
strength 0 – 3 0 = not mentioned, 1 = alternative, 2 = secondary, 3 = primary recommendation
context_quality 0 – 3 0 = not mentioned, 1 = errors, 2 = accurate, 3 = current details

GEO Score Formula

Composite score per (model, segment, competitor):

GEO_Score = (mention_rate × 3.0)
          + (avg_strength_when_mentioned × 2.0)
          + (avg_context_quality_when_mentioned × 1.5)
          - (avg_position_when_mentioned × 0.3)

Then normalized 0 – 10 across the full competitor matrix.

Known Limitations

  • Sample size. 456 LLM observations is adequate for top-3 ranking, not for differentiating minor competitors. Top-3 is stable across re-runs; ranks 4 – 6 are noisier.
  • Recommendation, not conversion. A high GEO score does not equal a signup. Pairing with attribution is the natural next step.
  • No agent-loop coverage. This measures the chat-LLM layer (a developer asks an LLM what to use). It does not measure agent-loop recommendations (Cursor / Claude Code calling Firecrawl during code generation).
  • Self-enhancement bias. Firecrawl's structured extraction is the parser. Cross-model judging would be more rigorous; the current setup is an acceptable trade-off for v1.

Reproducing

# clone and configure
git clone <this repo>
cp .env.example .env                   # add your API keys
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# run the battery (~90 min, ~$60)
python -m geo.orchestrator --dry-run   # check plan first
python -m geo.orchestrator

# export and serve
python -m geo.score
cd dashboard && python -m http.server 8000
